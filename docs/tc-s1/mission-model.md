# Independently specified fictional EO mission

A single LEO multispectral spacecraft receives 48 independent image-product requests during a finite observation segment. One normalized CPU executes each request to completion. Jobs represent already eligible image tiles or candidate products, not actual neural networks or flight applications. The six class names are motivated by E1–E6 in [the evidence dossier](evidence.md).

Constrained compute is an experimental normalization, motivated by finite onboard resources, not a measurement of Φsat-2 capacity. Competing requests may arrive together. Cloud masks are individually useful outputs here; they do not cancel or enable downstream work. A disaster mapping job represents a street/access map from a preselected disaster scene. Wildfire jobs represent assumed actionable candidate-scene products; false positives and detection accuracy are not modeled. Marine anomaly value describes a timely operational product, not the physical disappearance of pollution.

Importance determines base usefulness and static mission priority. Urgency determines how usefulness changes after acquisition. An expensive disaster map can be important but slowly decaying; a cheap cloud mask can have low immediate value and short operational lifetime; wildfire work can be important, urgent **and expensive**. Fixed priority is coherent: wildfire > disaster mapping > marine anomaly > vessel detection > cloud screen > routine compression. It does not inspect decay or predicted completion.

The primary design crosses five mission mixes and four nominal offered-load regimes, ten separately seeded instances per cell. Each instance has 48 tasks. Its acquisition horizon is `ceil(sum(execution_cost_seconds)/nominal_load)`. Arrival times are independently mapped to integer seconds in `[0, horizon-1]`. This fixes the offered-load factor without varying task count or utility budgets mechanically. It does not guarantee local underload: random bursts can overload even the low nominal-load cell. The engine drains the workload; the acquisition horizon is not a simulation cutoff.

Deadlines are fictional technical acceptance limits, freshness is a separate fictional information-validity limit, and both are relative to each task's arrival. Input time equals arrival. Results are valued at compute completion using unchanged TC-0 semantics. No contact windows, communications, delivery utility, quality choices, dependencies, runtime uncertainty, energy/storage constraints, preemption, multicore execution or ML runtime are added.

Exact ranges, mix weights and factor definitions live in [the machine-readable preregistration](../../research/tc-s1/preregistration.json). They are D assumptions. The model is policy-independent, externally motivated, and wholly simulated; it is not an independent observed mission dataset.
